# The loop's contract

`workplace` is an interpreter of one expected form: six terms that it executes and two tables that it folds into each seat's start. It also assembles a clone for the reader and folds the plan's statements into a seat's view. It holds no code for any one primitive. What a term does is its entry in `host/binding.json`; what the loop does with any entry is below. Each sentence is shown by at least one check of `tests/run.sh` that carries its number.

## Inputs and the build

- **C1.** The loop reads two variables of its own and no other setting: `WORKPLACE_ROOT`, the absolute path of a directory, and `WORKPLACE_CONFIG`, the absolute path of a directory at or below it. Each is taken as its physical path exactly, a final newline included, and never as another directory's, so that A14 sees the base name as it is (5.144 point 5) and a root whose name ends in a newline is refused with exit 2 rather than read as another directory: for its control character, or by A14 first where the clone is the root and the workplace's name is derived from it. At 09ec4f6 a final newline was dropped. The frame's own directory, from which it reads its programs, is taken the same way. A root, a name or a configuration's path that holds a control character, C0, DEL or C1 (5.159 point 6), is refused with exit 2. Anything else is refused with exit 2. For the workplaces' state directory it reads the platform's `XDG_STATE_HOME`, else `HOME` (C35). Every tmux call names the socket by its recorded path (C68). At `up` only, `TMUX_TMPDIR` chooses the default socket of a `tmux-default` floor; later commands use the recorded path.
- **C2.** `build` reads `PLAN/` in `WORKPLACE_CONFIG` and nothing else:
  - `plan.json` is the reader's output as printed;
  - `facts.json` is the facts it was planned on;
  - `manifest.json` is the root, the inputs and the outputs, each with its sha256.
  - It refuses, naming the file or the fact: a missing file; a changed input or output; outputs that do not list `plan.json` (and `facts.json` when there is one); a root other than `WORKPLACE_ROOT`.
  - When the plan's `facts` member is `none`, it compares no fact.
  - When the member is a digest, `facts.json` must have that digest and belong to the same root, with canonical paths and v1's five facts only. Its own collector then reads again each fact the file records, and refuses one that no longer holds; an entry the file does not record is no difference.
  - It prints the manifest's reader and derivations.
  - `build` writes `BUILD`: the plan, its facts and manifest, the binding, the loop's own files, and a `MANIFEST` of their hashes, each equal to its source.
  - It refuses while `BUILD` exists, and a failed or interrupted build leaves no `BUILD`. `unbuild` removes one while the workplace is down (C99).
- **C3.** The plan is refused at build for:
  - a status other than `ok` or `unchecked`, or a control character in any string or member's name: C0, DEL or C1, the class the fold and the names take (5.159 point 6);
  - a term with no binding, outside the binding's order, or of the wrong arity;
  - a value that a term gives for a closed set, such as a layout, outside its set;
  - a command that is not a JSON list of strings whose program is a bare name or a path (C4);
  - a name that is empty, holds `/` or begins with `-`;
  - a state row that is not four strings and one value, names a seat the plan does not make, or holds an unknown state;
  - two seats of one name, and a key that is not one (C67);
  - and against the binding's structure: not exactly one `server`; two `session` terms for an office, two `window` or `arrange` terms for a room, two `pane` or `start` terms for a seat; a session with no window, a window with no pane or arrangement, a pane with no window or no start, and the reverse. Each such refusal names each term it rests on, by its file and place.
- **C4.** A path that a term, a recorded term or a row gives as a place on the machine is written absolute or relative to the root, and the plan keeps it as written. The frame joins a relative path: the root, a slash and the path, where `.` is the root, with no doubled slash under the root `/` and never `/.`. An absolute path is taken as written.
  - The places are the binding's: each `path` argument of a primitive; the program of a seat's command when it holds a slash; and those under `paths`, which are a statement's and a label's path, a claim's, a recorded directory, and a row of the `view` cell. The root that the plan's `configure root` records is not joined again.
  - A bare program is looked up on the seat's path. The other words of a command and every value of the environment are text, and are not touched.
  - A path with an empty component, a `.` or `..` component other than the single `.`, or a slash at its end is refused by `plan` and by `build`, with exit 1, naming the term or the row's origin.
  - `view.json`, every row, the fold and everything `build` writes carry the joined path, and `why` prints the path as written beside the joined one where they differ.
  - A program's and an origin's `path` are the reader's record of where a line was written, and the loop neither rewrites nor refuses them.
  - A `read-only` or `read-write` row whose path does not exist is refused, and so is a `hidden`, `searchable-only` or `scratch` row whose path is not a directory. The preconditions the binding names (a directory, a file) are checked at build.
- **C5.** `up` checks `BUILD` against its `MANIFEST`, refuses a changed, missing or unlisted file, and never builds.
  - **With floors** (5.160 point 2), `BUILD/MANIFEST` is the top: it names the frame's files (`binding.json`, `bin/workplace`, `libexec/*.jq`, and `seat-page.md` with mail), one shared generation `shared/N/MANIFEST` and one generation `floors/F/N/MANIFEST` for each floor, in the order of the floor terms, and nothing else. Each line is a hash and a name, the name as it is, so that a floor's key that holds a backslash, which C67 lets pass, is named in the top as it is written and its build verifies (stop 4a's review). `BUILD/shared/N` holds the plan's copies (`plan.json`, `plan-manifest.json`, `plan-facts.json`, `plan-view.json`) and `mail.json`; `BUILD/floors/F/N` holds the floor's `keys.json`, `homes.json` and `records.json`; each generation's `MANIFEST` lists its files. A build's generations take one number, the counter's in `S/generation.next`, which `build` makes empty, so that its first number is 1, and the counter then goes up by one, so that no number is taken twice (5.162). A counter that holds anything but a number refuses `build` with exit 1, naming it. The top is written last, by one rename. Every reader of the build reads the plan's copies and `mail.json` through the top, and none stands beside it.
  - The check verifies the top, the frame and every generation the top names, and refuses a changed, missing or unlisted file anywhere in `BUILD`, a top whose floors are not the plan's, a top or a generation's MANIFEST with an empty line, and a top that holds a NUL byte.
  - A command of one floor (`up F`, `restart F`, `status F`, `carry F`, and `exec` of a seat of F) reads the top once, its bytes and their hash in one read, and verifies the top, the frame, the shared generation and the floor's own generation alone, so that a fault in another floor's generation does not stop it (5.160 point 3). A bare `status` verifies them all.
- **C6.** The loop needs bash 5.2, jq 1.7 and tmux 3.5a or later, and refuses an older one; versions are compared with tmux's letter suffix, so the floor 3.5a refuses 3.5. It needs `setpriv`, `env`, `mkdir`, `cp`, `rm`, `sha256sum` and `stat`, and bubblewrap only when a seat has a view; where a seat's view holds a row, the rule on closed names reads its real path with `readlink` and `stat`, and refuses where either is not on PATH (C31, 5.177 point 6). GnuPG 2.4.4 or later (`gpg`, `gpg-agent`, `gpgconf`, `gpg-connect-agent`), with `setsid` and `base64`, is needed only by a plan in which a seat holds a key (C44), and OpenSSH's `ssh-keygen` and `ssh-add` only by one that grants an ssh key (C86), GNU `env` with `-S`, coreutils 8.30 or later, only by one in which a seat expects a value (C49): `up` and `exec` refuse an older `env` there with exit 2, naming both versions; and git 2.32 or later, with `flock`, `dd`, `mv`, `tail` and `date`, only by a plan that holds mail (C56). It resolves each program to an absolute path before it applies anything, and refuses a path that holds `=`.

## Applying the plan

- **C7.** Every value the plan or a slot gives a tmux command is encoded: a backslash before a trailing `;`, and where tmux expands formats, every run of `#` not followed by `[` doubled. The program's own options (`-L`, `-f`) are not encoded, since tmux's command parser never sees them. No text of the plan is evaluated by a shell.
- **C8.** Terms are applied in the binding's order of primitives (`server`, `workplace`, `floor`, `house`, `session`, `window`, `pane`, `arrange`, `start`), and in plan order within one primitive, whatever the order of the plan's programs. Each office gives a session, each room a window and a layout, each seat a pane and a start in its first directory. A pane is made by splitting its room's window, which is then re-spaced with tmux's `tiled` so that the next split has room. The room's declared layout is applied once, by `arrange`, after all its panes exist, and the room ends in that layout.
- **C9.** tmux's first window of a session and first pane of a window are claimed by the first `window` and `pane` terms that ask for them. Panes are appended in declaration order, and `up` refuses when a window or pane that is not a seat would stand. Every target is a captured id.
- **C10.** Without floors, and on an enforced floor, every tmux call runs under `setpriv --no-new-privs` with `TMUX` and `TMUX_PANE` removed, so the server and every seat run without privilege gain. A running enforced server without no-new-privileges is refused. An unenforced floor instead requires its server and caller to have `NoNewPrivs: 0`; its seats retain ordinary privileges, while agents, carriers and keepers keep the bar. The check names the process it checked: the tmux server, an agent or the carrier. A process that has ended by the time its status is read is a refusal of its own, which says so. The server's socket stands in `RUN` (C68), so no server that `up` did not start stands there when `up` starts.
- **C11.** Without floors, `server` checks, before any session exists, that `destroy-unattached` and `exit-unattached` are off and `exit-empty` is on. With `exit-empty` off, the empty server its check started stays and nothing else is made: the loop never ends a server, and the refusal names the server's socket and the command that ends it, and keeps `RUN`, which holds the socket, while the server stands. Every session carries the run's mark, `@workplace`. A new floor server temporarily keeps `exit-empty` off through its admission, then sets it on with its first session; an existing default server keeps it on throughout.

## A seat's view

- **C12.** A seat's view is the table of the plan's `view` cell, read in one place. A seat with rows starts in bubblewrap with its own user, PID, IPC and device namespaces. The emission order is: the row for `/`; then a fresh `/proc` and `/dev`; then the other rows in the byte order of their paths. A seat with no rows starts without bubblewrap.
- **C13.** A row that is not `hidden`, lying beneath a `hidden` row by path components, refuses the seat's table whole, naming both paths. `/a` and `/ab` are separate branches.
- **C14.** The states:
  - `hidden` is a tmpfs of mode 0000, and nothing beneath it exists;
  - `searchable-only` is a tmpfs of mode 0111: it can be passed through, not listed, and only its rows exist;
  - `scratch` is an empty writable tmpfs;
  - `read-only` and `read-write` bind the path onto itself.
  A path with no row has its nearest ancestor's state, and every table of a seat holds a row for `/`.
- **C15.** Inside a view, `/dev/tty` opens, the terminal's size can be read, job control works, a full-screen program reaches the alternate screen, and another pane's terminal cannot be written.
- **C16.** A seat's program receives exactly the binding's inherited names and the rows of the plan's `environment` cell for that seat, then the variables that the frame gives it (C39, C48) and the values it expects (C49). Without floors an inherited name takes its value from the environment `exec` runs in. With floors it takes the value captured from the `up` caller, before tmux can inject its own environment. `PWD` is the seat's directory. A variable of the server or of the loop does not arrive.

## exec, down and the run

- **C17.** A pane's command is `workplace exec -- SEAT` and nothing else. `exec` checks `BUILD` first. It starts the seat's program with the view, the environment's rows and the inherited names, captured in the seat's record with floors and read from the caller without floors, from any terminal and any directory. `--print` prints the call that `exec` makes, word for word, and an unknown seat, a changed build or a workplace that is not up is refused with exit 2. With floors `exec` finds the seat's floor in the build's plan, verifies that floor's build (C5) and reads that floor's run (C21), and a seat whose floor is not up is refused with exit 2 (5.160 point 8). A pane holds a silent tmux client until its start replaces it with `respawn-pane -k`, which is followed by clearing its history. No key is sent to a pane but by the carrier, which types a seat's write request where the plan allows it (C60) and its own pointer to delivered mail where the reader's kind has a wake (C94), both through one function.
- **C18.** `down` undoes, newest first, what `up` recorded and nothing else. It acts only on a session that still carries the run's mark, removes `RUN` and keeps `BUILD`, and with nothing up it does nothing. It reaches the run's server by its socket's path, whatever the shell's `TMUX_TMPDIR`. When the server still holds sessions that the run did not make, it leaves them, says so, and keeps `RUN`, which holds the socket, while the server stands. It keeps `RUN` and exits 1 when an undo fails.
  - With floors (5.160 point 8), `down F` takes the floor F down alone: its carrier, what its `up` recorded on its own server, and `RUN/F`. The other floors stay up, and `RUN` stays. `down` of a floor that is not up says so and exits 0. With floors a bare `down`, or one of two floors, is refused with exit 2, and so is a floor the build does not make, unless its `RUN/F` stands.
- **C19.** A failed term stops `up`. Everything made in that run is torn down by its captured id, whether or not its mark was set yet, `RUN` is removed, and the failure names the term.
- **C20.** `up` refuses while `RUN` exists. With floors `up F` refuses, with exit 1, while `RUN/F` exists, and while another `up F`, `down F` or `restart F` holds the floor's lock, naming that command and its process (C102); every one of the three refuses so too.
- **C21.** `RUN` holds:
  - every call made;
  - the undo ledger;
  - the checks `status` runs;
  - each seat's recorded start;
  - the tables;
  - the learned slots;
  - the carrier's directory, which is its working directory and its mark, and its log (C57);
  - the server's socket (C68).
  It is the loop's record and no input of the reader.
  - With floors each floor's run is `RUN/F` (5.160 point 8), and what this contract says of `RUN` it says of `RUN/F` for that floor's commands. It holds the list above for the floor, and also `tmux.conf`, copied from the generation's sealed `floor.conf` for server startup (C105). Its `state.json` names the floor, the top's hash and the generations that `up` read.
- **C22.** `status` reports the build, the run and every check as ok or gone, and exits 1 when the build has changed or a check fails. With the run up, it prints the line that attaches to the server.
  - With floors, a bare `status` reports the build and then each floor in the floors' order, and `status F` the build, the mail's and the values' lines, which are the configuration's, and the floor F alone: its homes, its records and its run. After the build's line it prints `shared  generation M`, the shared generation that the top names. For each floor it prints `floor   F: generation N`, a `conf` line naming its sealed file and the frame's settings after it, and `run: floor F is up, ID` or `run: floor F is down`. A running floor also gets a read-only check of its transport settings (C106). For a floor that is down, where requests of its writers wait in `out`, a `waiting` line counts them and says that none is served until `up F`: no other floor's carrier serves them (C57). It exits 0 for a floor that is down.
  - With floors and mail, where `S/store.holder` stands (C57), the mail's lines end with a `store` line. Where the process that the file names runs as the carrier of the floor that it names, the line says that this carrier holds the store's lock, since when and for which request; otherwise it says that no carrier of that floor runs as that process, and that the next hold replaces the file. `status` takes no lock to tell them, so that it never costs a carrier its pass. It exits 0 for either.

## Questions and the host

- **C23.** `why SEAT PATH` prints the row that decides a path for a seat, or its nearest ancestor's, with every claim behind it and each claim's origin, losing claims included.
  - For a path with no row it says what the nearest row above means for the path: beneath a read-only or read-write row the path is as the machine has it, with that access; beneath a hidden row the seat cannot reach it; beneath a scratch row it is not there until the seat makes it; beneath a searchable-only row it is not there and the seat cannot make it.
  - Where a row lies beneath the path, beneath a searchable-only row the path is a directory the seat passes through to that row and nothing more, and beneath a scratch row it is a directory of the seat's scratch made to hold that row.
  - Where a mask of the frame covers the path, it says that the mask decides and the row does not. The mailbox is such a mask (C55).
- **C24.** `doctor` reports each program with its version, whether no-new-privileges can be set, whether bubblewrap can make a user namespace, whether the kernel lets a program push input into its terminal (TIOCSTI), git and the programs that a plan that holds mail needs (C56), and the programs a chain to the journal needs and whether a user manager answers (C72). When the host refuses the namespaces, it names the host's one root step and never takes it.
- **C25.** A workplace's tmux server is named by the plan's `server` term. The name names the workplace's state directory, its carrier's unit and its socket in `RUN`, and `default` is a name like any other. For any other name, `build` derives the name again by the rule that the manifest names as `derivations.workplace-name`, and refuses another name, a missing rule or a rule it does not know. The rule it knows, `sha256-path-prefix12-v1`, is the clone's directory name, a dash, and the first twelve hex digits of the SHA-256 of the clone's absolute physical path. Two workplaces never meet, since each run's socket stands in its own clone.
- **C26.** The loop sets the C locale before anything else, so that no result follows its caller's locale: the names `stat` gives a file's type and the messages of the programs it calls are C's. tmux runs with the caller's `LC_ALL` as it was, so that the server's environment is the caller's, and with `-u`, so that what tmux prints is never rewritten for a terminal without UTF-8. The test file sets the C locale too.

## The plan and the fold

- **C27.** `plan` reads the clone at `WORKPLACE_CONFIG`: `workplace.json`, the layers it lists, `programs/` and `tmux.conf`. It assembles in a directory of its own, which it removes.
  - The declarations are one `#lang typify` header and each layer's whole body after its header line, in `workplace.json`'s order. No line is edited.
  - The tree is a generated root program with a copy of `programs/` beneath it, and nothing else. The root program is exactly two lines: `workdir : ROOT` and `server : NAME : CONF`.
  - CONF is the path of `tmux.conf` relative to the root, and NAME is derived (C25), or `default` when `workplace.json` says `"socket": "default"`.
  - The reader cuts each line of the root program into words at a colon between spaces, and a word's class, which the layers declare, decides the rest: a bare `:` or `\` is one of the word's characters (5.142). So no word that the loop writes there holds a colon between spaces, or begins with a colon and a space, or ends with a space and a colon. `plan` refuses, with exit 2, a root that does, and a clone's path relative to the root that does as it heads a word (before `/` and a file name: inside it or at its start), each named; a floor's name and conf are C100's. Where the workplace's name is derived (C25), a clone's base name that does not fit the class of that name, `[A-Za-z0-9][A-Za-z0-9_-]*`, refuses too, named, except where its fault is a separator that the root's or the path's line has named. Anything else in a word is its class's business, and the reader refuses it at the generated program's line.
  - It refuses, with exit 2:
    - a layer with a byte-order mark, CR line ends, a NUL byte, no `#lang typify` header or no final newline;
    - a program with a byte-order mark or CR line ends;
    - an empty directory under `programs/`, which git does not carry, so the plan could not be made again from a clone;
    - a layer name listed twice, or a language declared twice;
    - a member of `workplace.json` that it does not read.
- **C28.** The reader is the program `typify` on the path.
  - `plan` runs the reader's `check` on the declarations, and stops on an error. It shows the error at the layer's file and line, beside the reader's own words and line.
  - It then runs the reader's `plan --json` on the tree, and keeps the output as printed. A program's error is shown at its path in the clone, and the root program's as the generated program's.
  - It records the first line that the reader's `--version` prints, and stops when the reader states none.
  - A plan whose `facts` member is not `none` is refused, since 5.15 leaves open which facts `build` compares.
  - `plan` exits 0 when `PLAN/` is written, 1 when the reader or the fold refuses, and 2 on a fault of its inputs. On a refusal, `PLAN/` stays as it was, and `plan` never touches `BUILD`.
- **C29.** `PLAN/` holds the following, and `build` checks them:
  - `plan.json`;
  - `view.json`, exactly when the plan holds statements, clearances or labels, all of which the fold reads. A `plan` that writes none removes the one before it;
  - `manifest.json`: the root, the name, the reader, each derivation's version, every input with its hash in a fixed order, each generated file with its hash, the source map and the outputs. The fold's version is `frame-5.17-5.18-5.24-5.29-5.37-5.50-5.54-5.66-5.78-5.122-5.124-5.125-5.126-5.129-5.131-5.132-5.141-5.146-5.153-5.162-v18`.
  - `plan` writes `manifest.json` after the outputs, and `build` refuses an output that is missing or whose hash differs from the manifest's, naming it. A `PLAN/` left half-written is never built.
  - `build` needs no reader. When the clone holds `workplace.json` or the manifest lists generated files, it assembles again, with the refusals of C27. It refuses a different name, an input that was added or is gone, and a generated file that differs, each by name.
  - It folds `plan.json` again, and refuses a `view.json` that differs, naming the seats and both fold versions, and saying to plan again. Where the manifest names another fold and the views are equal, it says so in one line and goes on.
- **C30.** The fold reads the plan's `statement A B C SCOPE PATH STATE`, `clearance A B C SCOPE NUMBER`, `clearance-scale turned`, `label PATH NUMBER`, `key A B C SCOPE STATE`, the four terms of C45, `mail` and `reach` (C54), and the four terms of C69 from the programs' `recorded` lists, in the plan's order. It takes the seats from the `pane` terms and each seat's kind from the `seat-kinds` cell. For each seat:
  - its statements are the workplace's, its kind's, its office's, its room's and its own;
  - equal statements, clearances and labels count once, and carry the origin of each;
  - a statement is replaced by a narrower one at its path or at a directory above it, by components, and those that remain are the seat's rows;
  - its clearance is its room's, else its office's, else none, and a seat with none is cleared for no label. A seat carries no clearance of its own (5.118).
  - A clearance is a whole number of at most 15 digits, and 0 is the most cleared (5.122 point 1). A label is a whole number of at most 15 digits, or `closed`. At that size every number the frame compares, in jq or in the carrier's bash (C94), compares exactly. A seat is cleared for a numbered label when its clearance is at most the label, and for a `closed` label never (5.124 point 6).
  - Labels are taken from the shallowest. Where the seat has no row at a labelled path, the label asks two questions, each answered by a row of its own (5.129 point 2):
    - Does it lie beneath a path that a statement hides or makes scratch? The nearest row above it that a statement made answers, passing over the rows that labels made. If it does, the label makes no row: no hidden row, no read-only row and no passage (5.126 point 2).
    - If not, which row does it make? The nearest row above it of any source answers, a label's row among them. When the seat is not cleared for the label, it makes a hidden row, and none when that row is searchable-only. When the seat is cleared, it makes a read-only row.

    The row a label makes replaces nothing.
  - A hidden row that a label made becomes searchable-only when a row that is not hidden stands beneath it. It is then a passage to what lies beneath (5.124 point 7): a label beneath a labelled path governs that path.
  - the rows stand in the byte order of their paths, each with the origins of the statement or label that made it, in the plan's order (5.18): equal statements at several scopes make one row whose origins follow the plan, whatever scope each stands at (5.131 point 4).
- **C31.** The fold refuses the plan, naming the seat, the paths and the origins, for:
  - **Read on the machine, beside the fold** (5.159 point 6, 5.162 point 6, the addendum's 2(3)). The fold reads paths as written; `build`, `up` and `restart` refuse with exit 1, and `exec` with exit 2 for its seat, from the clone's frame or from `BUILD`'s own copy, which a pane runs, a view that would hold a closed directory under another name. The closed directories are the labels of closed and the frame's own masks: the clone (C52), R (C39), the user's tmux socket directories (C68), the journal's directories where a chain is kept (C73), and the runtime directory (C84), beneath which a seat's rows are mounted again after its mask. It refuses:
    - a label of closed written through a link, since a tmpfs written through a link lies where the link leads, and one whose last part is a link gets none, as bubblewrap mounts nothing on a link; such a refusal names the label, its origin and, where it has one, its physical path;
    - a row that is not hidden whose real path is at or beneath a closed directory's, unless it is written at a mask's path or beneath it, where the mask lies, the runtime directory's included; a row that leads to a mask from another name, a link's spelling of it among them, is refused (5.177 point 6). The frame takes the clone, R and the tmux socket directories by their physical paths, so each mask lies at the path the rule reads, whatever of a link a seat's view shows;
    - a read-only or read-write row whose real path holds a closed directory, where the row would show it, at its written path joined with the rest of the closed directory's physical path, and nothing lies over that path after the row's bind: neither a hidden, scratch or searchable-only row of the view written at it or at an ancestor of it beneath the row, which the order of the rows mounts after it, nor, for a mask, the mask itself, which is mounted after every row at its path. A label beneath a hidden, scratch or searchable-only row has no tmpfs of its own, and that row is what lies over it.
    A row is judged by its real path, where every link in it leads, its last part too, a file as well as a directory (5.176 point 7); a directory is resolved without being entered. A row, a label or a mask whose real path the rule cannot tell, or of which it cannot tell whether it stands because a part of its path cannot be searched, is refused, naming it and the reason (5.177 point 6). Each row's refusal names the seat, the row with its state and origins, the file or the directory that it leads to, by its real path, and the closed directory's physical path, where a row holds one the path where it would show it, and the label's origin or the mask's name. A path that does not exist is passed over, and so is a mask that does not stand.
    The views it reads are those a pane gets, the seat's table of C33: `view.json` where the plan holds statements, and the plan's `view` cell where it holds none, so the frame's masks hold under another name in that cell too (5.176 point 7). It reads the plan, the views and the binding that joins the labels' paths: at `build` the frame's own binding and library, and at `up`, `restart` and `exec` `BUILD`'s own copies, which `BUILD`'s manifest verifies, so that a binding or a library of the checkout changed after the build is not read there (5.176 point 11). It joins the labels to the command's root, and `up`, `restart` and `exec` refuse, before anything is made, a root that is not the plan's, as `BUILD`'s copy of the plan's manifest names it, where another spelling of the same directory is the same root, with exit 1, and `exec` with exit 2: `COMMAND refuses: the plan belongs to the root ROOT, not to ROOT2`, or `COMMAND refuses: cannot read the plan's root in FILE` (5.177 point 6). Where it cannot read the plan's labels or the views, and where a label is no absolute path once the binding joins it, it refuses.
    Its limits (5.176 point 7, 5.177 point 6): a directory that the machine mounts at a second place is not seen; it reads the machine at one moment, before the bind; a hard link to a file beneath a closed directory is not seen, since it reads paths; at `up` and `restart` its own code is the checkout's, which nothing compares with `BUILD`'s; and its verdict rests on the command's environment, the state's and the sockets' directories, and the `jq`, `readlink` and `stat` on its path.
  - a statement at the scope of a kind that the plan does not make, as a home and a wake of such a kind are refused. `none` is such a kind: it is the fold's word for a seat with no kind, and no kind is made so (5.131 point 4);
  - a term of the wrong shape, an unknown scope or state, a path that is not canonical, a number that is not whole, a label that is neither a whole number nor `closed`, or a clearance or a numbered label of more than 15 digits;
  - a clearance at a seat's scope, since a seat has its room's clearance (5.118);
  - clearance or label terms with no `clearance-scale turned` term, naming the first three origins of the clearances followed by the labels. A configuration numbered before 5.122's turn is refused, until it is renumbered and says so;
  - a `clearance-scale` of other words than `clearance-scale turned`;
  - a label beneath a `closed` path;
  - a statement or clearance that names an office, a room or a seat that the plan does not make;
  - two statements of one scope about one path with different states, two clearances of one scope with different numbers, or two labels of one path with different values, `closed` and a number among them;
  - a label on `/`;
  - a seat with no row for `/`, checked before any label is taken;
  - a row that is not hidden, lying beneath a hidden row;
  - a row that is not hidden, whose governing label is one the seat is not cleared for. A row's governing label is the deepest label at or above it, and a passage is not refused.
  - a label the seat is not cleared for, whose path has no row of the seat's, and whose nearest row above is read-only or read-write: `seat NAME (K/R/S): PATH, labelled VALUE (from ORIGIN), lies beneath ROW (STATE, from ORIGIN) with no row of its own`, then `, and no clearance reaches closed`, `, and the seat is cleared for no label`, or `, and the seat's clearance C does not reach VALUE`. This checks what the label step made (5.129 point 2): the rule above reads the labels at or above a row, and this one reads the labels beneath one. A row at the labelled path itself is the rule above's.
  In addition to that closed-name check, `build`, `up`, `restart` and `exec` check
  alias access on the machine. The first three check all views; `exec` checks its
  selected seat. They read the same plan, view and binding as the closed-name
  check. `libexec/alias-access.jq` is copied into BUILD and covered by its
  manifest. The existing closed-name refusal is returned first.

  Host contents have three access levels: unshown, read-only and read-write.
  Hidden, scratch and searchable-only rows give no access to their host backing
  contents. Each host bind is checked against the deepest canonical own-name
  permission, the governing label, private-key source files and frame masks. A
  cleared child label or explicit writable child remains an exception at its own
  path. A cleared label alone grants reading, never writing. An uncleared label
  remains a restriction even when the fold made no row for it beneath scratch
  or searchable-only ancestry. No alias makes a read-only path writable.

  A directory bind must preserve stricter descendants too. Each is projected
  onto the bind's written destination and needs a later cover there. The deepest
  standing row decides: an earlier scratch cover does not excuse a later bind
  reopening the protected contents. A read-only submount can preserve a file's
  read-only access beneath a writable parent alias. A cover can stand above the
  projected restriction, strictly beneath the introducing bind. A protective row
  written through a link is accepted only as such an independently anchored,
  symlink-free projection. It cannot define a different canonical restriction or
  justify another unanchored cover. Labels and declared private-key source paths
  must be written without symbolic links, including their parent components.
  Checking a private-key source reads metadata only, never its contents.

  The runtime-directory restriction is checked again at every admission point,
  including on a build changed by hand. Its mask is not a terminal cover of rows
  emitted again by rows-beneath after the mask. Read-only and read-write rows in
  that directory refuse; hidden, scratch and searchable-only rows keep their
  existing rules. A final mask can bury an earlier row only where the renderer
  actually places it. It does not authorize an outside alias to the masked host
  path.

  A command caches path-presence and real-path results only within that one
  admission check. Non-absolute, looping, unreadable or indeterminate metadata
  refuses; a missing bind source still fails the existing build checks. No
  directory is walked and no mount is injected to repair an invalid view.
  `build` also reports admitted aliases which stand at or expose a numbered
  labelled path, with written and resolved names and their origins. This report
  does not change the reader's source accounting or the persisted view.

  These checks require stable path components and host mount topology from
  inspection to the bind, and no replacement of protected objects beneath a
  running view by external host work. They do not identify hard links, duplicate
  host mounts or already-held descriptors. The checkout, caller environment and
  trusted-tool limits above remain. No continuous filesystem guarantee follows
  from a successful admission check.

## A seat's home and the values at run time

- **C45.** The fold reads four terms of the plan's `recorded` lists.
  - `home KIND VARIABLE STATE`: a seat of the kind has a home, named to its program through VARIABLE. STATE is `kept` or `scratch`.
  - `home-variable KIND NAME SUBPATH`: a further variable, given the directory SUBPATH inside the home. SUBPATH is relative to the home, with no empty, `.` or `..` component; `.` alone is the home.
  - `home-seed KIND PATH`: a program that `build` runs for each kept home it makes. PATH is a path position of C4.
  - `expect A B C SCOPE NAME`, with SCOPE `workplace`, `floor`, `office`, `room` or `seat`: the seats of that scope expect the value NAME, an environment variable, at their start. A seat expects the union of the names that the workplace, its floor, its office, its room and its own terms state; none takes a name away, and equal terms count once with all their origins.
  - `view.json` gives a seat of a kind with a home `home: {kind, variable, state, variables, seed, origins}`, and a seat that expects a value `expects: [{name, scopes, origins}]`, by name. A seat with neither has neither member, so the view of a plan without these terms is the one the fold gave before.
  - It refuses, naming the origins: a kind no seat has and the plan does not declare; a name that is not a variable name; a state other than `kept` or `scratch`; two homes, two variables of one name or two seeds of one kind that differ; a variable or a seed for a kind with no home; a variable that is the home's own; a seed for a scratch home; an expect of a place the plan does not make or of another scope. A refusal that rests on two terms names the origin of both: a variable that is the home's own names the variable and the home, and a seed for a scratch home names the seed and the home.
  - A kind's name and a seat's name are each one directory of its home's name, since neither is empty, `.` or `..` or holds `/` (C67).
  - The names the frame keeps are the binding's `kept-names`, the names its fixed part gives a seat itself: `GNUPGHOME` and `SSH_AUTH_SOCK`. A home's variable, a further variable or an expected name that is one of them is refused. So is an expected name that the binding passes on from the caller, such as `HOME`, since that would cover the value; a home may use such a name.
  - It refuses a seat that expects a name its kind's home gives it, naming the seat and both origins.
- **C46.** A home is named by its seat's kind and name, never by the seat's place among the panes or its coordinate (5.124 point 2): `S/homes/KIND/NAME`, where S is a floor's state with floors (C102). No two seats share it, since a name is one seat's, holds no `/` and is not `.` or `..` (C67). `build` makes a kept home with mode 0700, each directory above it in `S/homes`, and `S/homes` itself, also 0700, and keeps it across builds.

  - A scratch home has the same path and nothing on the machine.
  - `BUILD/homes.json`, listed in `BUILD/MANIFEST`, holds for each seat with a home its keys, name, kind, state, home's name, path and variables.
- **C47.** For each kept home that `build` makes new, it runs the kind's seed once, under `setpriv --no-new-privs`, in the home, with nothing on standard input. Its words are the home, then the seat's start directory, then its declared directories, joined, each once: the start's directory is the seat primitive's, and the declared ones are the recorded term that the binding's `directories` names, `record-directory`. A directory that is both the start and a declared one stands once, first, and a seed is given no mark of which word is which. Its environment is the inherited names and the home's variables.

The record keeps the words each home was seeded with, and a later build that finds other words for the seat says so in one line, naming the seat and both sets of directories; it does not refuse and does not seed again. Its new home is removed. A seed that is not an executable file refuses the build before the home is made.

It goes down from the home one name at a time and makes what is missing. At a link, or at something that is not a directory, it makes nothing for that variable, and says so in one line naming the variable, the seat and the path. It makes none in a scratch home (the limits).
- **C48.** After the rows and inside the mask on R, the binding's fixed part shows a seat its home at the home's own path: a kept home read-write as the machine's directory, and a scratch home as a file system of mode 0700 made when the pane starts, empty, of which nothing is left when the pane ends. No other seat is shown it.
  - The frame gives the seat, after the environment's cell, the kind's variable with the home's path, and each further variable with its path inside the home.

## A server belongs to one clone

- **C53.** The `session` term marks its server with the clone, as the global user option `@workplace-clone`. The mark lives in the server's memory and nowhere else, so it ends with the server.
  - The server's socket stands in the clone's `RUN` (C68). So when `up` starts, no other clone's server and no earlier run's stands there, and two clones that name the same server each have one of their own.
  - `status` reads the mark, and exits 1 for another clone's mark or for none. A server that lost its mark is told from one that never had it by the process id that `up` records once its terms are applied: the run's own process with no mark is reported as such, and another process as another.
  - `down` refuses, keeping `RUN`, a server that carries another clone's mark. For a server with no mark it says so and goes on, since each undo checks its own mark.
  - The mark is the clone's resolved path, so a clone is moved only while its workplace is down.
  - With floors each floor's server carries the mark, and a floor of rooms has a session of its own, made as a `session` term of the floor's key and the floor's name (C101).

## The Comms layer: mail, grab and write

- **C54.** The fold reads `mail PATH`, once for the workplace, and `reach A B C SCOPE ACTION TA TB TC TSCOPE STATE`. ACTION is `mail`, `grab`, `write` or `record`, STATE is `allowed` or `banned`, and each scope is `workplace`, `floor` (C103), `office`, `room` or `seat`, with `-` for the keys it does not use.
  - **Without floors,** for one asking seat, one action and one target, of the terms whose scope holds the seat, whose target holds the target and whose action is that one, those of the narrowest asking scope are taken, and among them the one of the narrowest target. Its state decides. With none, a seat may mail every seat, and may grab and write none.
  - **With floors** (5.132 point 1), a cell that any ban holds is banned, whatever allows it; else the narrowest allow decides, as above; else the default:
    - **An asker on an enforced floor** has its defaults by the relation of the target's room to its own, read from the rooms' numbers (C30), where a room with no number is cleared least (5.122 points 3 and 6, 5.125 point 7). Toward its own room it grabs, and does not mail. Toward a sub-room, a room of its office that is cleared less, it grabs and mails. Toward a room of its office cleared more or as much, nothing, and a term that would open it refuses. Toward another room of a floor of rooms, another office or another floor, nothing but by a term. On a floor of rooms the numbers decide no reach. It writes no seat, and a term that would give it a write refuses.
    - **An asker on an unenforced floor** has no default: terms decide every action, mail included (5.132 point 5).
  - **Withdrawn by name** (5.125 point 8): 5.51's "Clearance says what a seat may read at a labelled path (5.4) and nothing else" and "One number is not made to say both what a seat may read and whom it may direct", and this contract's "No clearance is read". 5.122 point 3 holds in their place.
  - `view.json` gives the mail path with its origins, and each seat `reach`: for each action, the names of the seats it may reach, in the plan's order; with floors an enforced seat's `write` is `[]`. `plan` prints the path and, for each seat and action, those seats, each with the origins of the terms that decide it, or, for a default cell, its ground: `its own room` with the room's number and origins, or `a sub-room` with both rooms' (5.132 point 10).
  - `plan` refuses, with exit 1, leaving `PLAN/` as it was and naming the origins:
    - a term of the wrong form, scope or state, or one that names what the plan does not make;
    - two `reach` terms equal in asking scope, target and action with different states, and two `mail` terms with different paths (equal ones count once);
    - `reach` terms with no `mail` term;
    - a seat with no row for `/` in a plan that holds either term, since a seat with no view could write as any seat;
    - with floors: a `write` term, allowed or banned, whose asking scope holds a seat of an enforced floor (5.125 point 10); an allowed `record` term whose asking scope holds one (5.124 point 9); and an allowed `grab` or `mail` term that decides as allowed a cell of an enforced seat toward a room of its office cleared more or as much, naming the term, both rooms and their numbers, once for each pair of rooms, by the asking room and then the target room (5.132 point 2, 5.141 point 7). A ban toward such a room stands.
    - with floors, after the seats are folded and only where those refuse nothing: an enforced seat whose finished reach holds a write or a record, or a grab or a mail toward a room of its office that is neither its own nor a sub-room, naming the seat, the action and the target (5.141 point 4). The fold as built never leaves such a table; the line stands as F9 does, to show a fold that errs.
- **C55.** After the rows, the binding's fixed part shows each seat its own mailbox at the mail path: a file system there, holding `out` read-write; `in`, `sent` and `answers` read-only; and `README.md`, the frame's page for a seat (C97), read-only; and read-only itself. No seat is shown another seat's.
  - `plan` refuses, with exit 1, naming the origins: a statement or a label at the mail path or beneath it; a mail path that is `/`, lies at or beneath the clone, or lies beneath a hidden row of a seat's table, which the seat could not pass; and a seat whose directory or program lies at or beneath it.
  - `build` refuses a mail path that is not a directory on the machine, and one that lies in the workplaces' state directory R or holds it. It refuses one that holds a control character, a character that moves or breaks a line, or bytes that are not UTF-8, as C58 refuses them in a head, since the pointer types the path into every seat's pane (C94). `up` refuses one that is no longer a directory.
  - Each of these refusals names the origins of the `mail` term beside those of what conflicts with it.
  - `why` names the mailbox for a path at or beneath the mail path.
- **C56.** The store stands in S, which no view holds. `build` makes it once and keeps it.
  - `S/mail` is a git repository made with no template, whose branch is `mail`. For each seat it holds a directory named by the seat's name, with `in` and `sent` (5.124 point 2). A name never begins with `.` (C67), so it is never `.git`, and git takes every path literally (C64). With floors the store is the configuration's, in S, and one for every floor (5.125 point 13).
  - Beside it, `S/comms` holds for each seat `out` and `answers` under the same name, `taken`, where the carrier keeps what it takes, the record, and `wake.json`, where it keeps the mail each reader has to be pointed out (C94). Every directory is the user's, with mode 0700, and the record and `wake.json` have mode 0600. With floors, `taken`, the serving journal and the request record stand in each floor's `S/floors/F/comms`, its carrier's own, and `S/comms` holds the shared boxes, `wake.json` and `next`, the counter of the ids (C57, C108).
  - `BUILD/mail.json` (with floors in the shared generation, C5), listed in the MANIFEST, holds the mail path with the origins of its term, S, and each seat's mailbox and reach, and, for a seat whose kind has a wake, its pattern (C93). With floors each seat's entry also holds its `floor`, its room's `number`, `null` where the room has none (5.132 point 9), and `own`, the item of its kind's `wake-own` for its floor's mode, `null` where it has none (5.146 point 2). Without floors it holds none of the three.
  - `BUILD/seat-page.md`, listed in the MANIFEST, is `build`'s copy of the frame's page for a seat (C97).
  - A plan that holds mail needs git 2.32 or later, `timeout`, `mktemp`, `cat`, `flock`, `dd`, `mv`, `tail` and `date`. `build` and `up` refuse it with exit 2 when one is missing, naming it. A plan without mail needs none of them.
- **C57.** The carrier is one process for the workplace, `workplace carry`. `up` starts it after the agents and before the first term, under `setpriv --no-new-privs` and in no view, and records it in the ledger and in the checks. With floors there is one for each floor that is up, `workplace carry F`, which serves its own floor's writers (5.160 point 8).
  - Its working directory is `RUN/carrier`, which is its mark. `down` ends it only while the process's working directory is that directory, waits until it has ended, and says it is gone when it is. A carrier whose mark is gone, its run directory removed under it, ends of itself at its next pass.
  - It holds a lock of its own for its life, `S/carrier.lock`, so a second carrier for the same store ends with exit 2. With floors the lock is the floor's, `S/floors/F/carrier.lock`, so one carrier serves a floor, and the floors' carriers share one store.
  - **The store's lock** (5.162 point 1). Each delivery is made under a hold of the store's lock, a `flock` on `S/mail`, one hold for one delivery: under it the carrier takes the next id from the counter, commits, writes the delivery's lines in the record and changes `wake.json`, entry by entry. So two floors' carriers deliver at one time on one store, and neither loses what the other wrote. Under the hold it decides again whether a request it chose before is still to be served, and it first unstages what no commit took, so that a stopped carrier's add rides into no other delivery. With floors it names itself as the holder in `S/store.holder`, which it removes when it lets go. It waits for the lock at most one second in a pass, and after a try that fails it tries no more in that pass: what it has not served waits for the next.
  - It takes no request until `up` has recorded the run. Then it makes a pass a second, serving the seats in the plan's order, one request of each per pass, and each seat's requests in the byte order of their names.
  - `status` names it, and exits 1 when it is gone, saying that requests wait. It counts the requests that wait, in all and for each seat that has any. While it is gone, requests wait in `out` and none is lost: the next carrier serves them. A request it was serving when it stopped is answered when it starts again, under the store's lock: the carrier finds the delivery's commit by its subject among the commits after the head that it noted as the delivery began, so that another floor's later commits do not hide it, and it removes what that delivery wrote and no commit took by the delivery's exact paths, and no other file. A mail whose delivery's commit stands is answered `ok`, and its line names the readers that commit gave it to, in the store's order. Before that line, in the store's order, the carrier decides for each reader it had not decided for, by a line in the record or an entry in `wake.json`. It decides by the build that is up as it starts again, not by the one of the delivery. A due reader's entry is dated by the commit, and a line of the record carries, as every line does, the time it is written. A reader whose seat that build no longer makes gets a `none` line saying so, and a writer whose seat it no longer makes withholds nothing: each reader decided for then is due where its kind has a pattern, and gets `none` where it has none (C94, C96). A line of the record that does not parse decides nothing. Where the commit's readers cannot be read, the `ok` line says so and nothing is decided.
  - Each carrier appends its own request record without taking the shared store's lock. Before appending it ends a last line that a stop left without its newline, so each new line parses by itself. The torn bytes remain as a line of their own, and the chain covers those bytes and the added newline (C72, C75, C108).
  - A request taken while it is still being written would be delivered cut short. Two rules prevent it:
    - An entry whose name begins with a dot is the seat's draft, and the carrier does not take it. A seat that wants certainty writes `.NAME` and renames it to `NAME`.
    - The carrier takes an entry only once its change time is at least one second old, so a request that a seat's file tool writes under its final name rests until it is whole. Until then the carrier takes nothing of that seat, so its requests keep their order.
- **C58.** A request is one regular file in `out`, named with letters, digits, dot, dash and underscore and ending in `.md`, `.grab` or `.write`, of at most 256 kB, which is 256,000 bytes.
  - Its head is lines `WORD: VALUE`: at most 20, each word once, of the words its kind knows, with no control character, no character that moves or breaks a line, and no bytes that are not UTF-8.
  - Every request gets an answer in `answers`, under its own name: `ok` and the request's id, or `refused` and the reason in words. A refused request does nothing.
  - The carrier refuses: a name of another form; an entry that is not a regular file; a file it cannot read at once; a larger file; a head of more than 20 lines, one with a line it does not know or a word twice, and one with no reader, subject or seat; a reader or seat the plan does not make, by its exact name; an action the table does not allow; a count outside 1 to 5,000; a text that is not one line, of more than 4,096 bytes, or with a control character; and a key outside the list.
- **C59.** A mail, `.md`, is a head with `to` and `subject`, and optionally `cc`, `re` and `reply`; a line of three dashes; and the body. `to` and `cc` name its readers, separated by commas, as the panes name them. If one reader is refused, the mail goes to none.
  - The carrier writes one file, `ID.md`, into each reader's `in` and into the writer's `sent`. Each holds `id`, the carrier's own time as `at`, and the writer as `from`; then the writer's other lines as they stood, with the writer's own `from`, `id` and `at` dropped; then the dashes and the body, byte for byte.
  - The delivery is one commit, by the carrier, and no commit is rewritten.
- **C60.** A grab, `.grab`, names `seat` and optionally `lines`, which is 200 unless stated and at most 5,000. Its answer is `ok`, the id, and what the pane showed: that many lines of history above the screen, and the screen.
  - A write, `.write`, names `seat` and optionally `key`, then has the dashes and one line of text. The carrier types the text into the pane as it stands, with `send-keys -l` and a trailing `;` escaped. Then it rests one second, looks at the pane again, and sends the key in a call of its own: `Enter`, unless the head names `Escape`, `C-c`, `Tab` or `none`.
  - The key goes apart because a program that reads one burst of input as a paste takes an `Enter` that comes with the text as a new line in what it holds, and the line is not submitted. The rest is the one that was measured to submit with the real program. During it the carrier does nothing else.
  - When the carrier looks again and the pane is gone, no longer carries the run's mark, is in a mode, or runs another program than before, it sends no key. The text stands typed and not submitted. The write is refused, its answer and its record say that the text was typed and its key was not sent, and why, and the record holds the text's length and SHA-256.
  - Both act only on the pane that the run captured for that seat, and only while its session carries the run's mark.
  - With floors, until S2's stop 4b, a grab or a write whose seat stands on another floor than its writer's is refused, with the reason `a grab or a write across floors comes with S2's stop 4b` (5.162 point 1).
  - A write is typed only into a pane that tmux shows in no mode (`#{pane_in_mode}`). A pane in a mode, such as copy mode, takes the keys itself and its program reads none, so a write to it is refused and recorded, with a reason that names the mode.
- **C61.** The carrier moves an entry out of `out` into `taken`, with floors its floor's (C56), which no view holds, by renaming it, before it looks at it. Before the move it reads the entry's name and its change time, and nothing else: not its content, not its kind. It never opens a name inside a seat's reach. It starts only when every `out` lies on the file system of `taken`, so that a move is never a copy.
- **C62.** It takes only a regular file. A link, a directory, a fifo, a socket or any other kind of entry is answered as refused and removed.
- **C63.** It reads the moved file once, into a file of its own, and works on that copy. The read follows no link, does not block, and stops one byte past the limit. What a seat changes afterwards through another name of the same file changes nothing, and a file held under a lease is refused at once rather than waited for.
- **C64.** It runs nothing that a request names. Names are compared with the plan's exactly, as text. A head, a name, a text or a body is never read as an option, a pattern, a format or a command: the text is typed literally, paths reach git as literal paths, and no word of a request reaches a shell.
- **C65.** The store runs no hook, and no seat can write into it. Git runs with a cleared environment, no system or user configuration and `core.hooksPath` set to `/dev/null`, so neither a hook in the repository nor the user's configuration runs. No view shows S.
- **C66.** The record is `S/comms/record`: one line of JSON for each request, served or refused, with the time, the id, the seat that asked, the request's name, the action, the target, the outcome and a refusal's reason. A write's line also holds the length and the SHA-256 of its text. Each pointer of the wake is one line of it too (C96). No line holds a body, a capture or a text. The mail's own record is its repository.

## Keys and names

- **C67.** A key of an office, a room or a seat, and a kind's name, is not empty, is not `-`, `.` or `..`, does not begin with `-`, and holds no `/`, no white space and no control character. `plan` and `build` refuse one that is, with exit 1, naming the term or the row. A name is one seat's alone: `plan` and `build` refuse two seats of one name, naming both terms. A seat's name, in every plan, is not empty, does not begin with `.`, holds no `/`, no comma and no control character, neither begins nor ends with white space, and is none of the carrier's own names beside the seats' boxes, `next`, `next.new`, `record`, `serving`, `serving.new`, `taken`, `wake.json` and `wake.json.new`, nor of the frame's own beside the seats' directories in the records, `chain`, `chain.state`, `chain.state.new`, `mark` and `mark.` followed by digits (5.162 point 5): `plan` and `build` refuse one that is, naming the term. The homes, the store and the Logs layer use a name as a directory's name, and a mail's head separates its readers by commas.


## No seat reaches a tmux server

- **C68.** The workplace's tmux server listens at `RUN/NAME`, in the clone, which no view holds (C52), and every tmux call of the frame names that socket by its path. With floors each floor that is up has a server of its own, at `RUN/F/NAME` (5.160 point 8). `up` refuses, with exit 2 and before it starts anything, a socket path of more than 107 bytes, naming the path and its length.
  - After the rows, in every view, the binding's fixed part masks the user's own tmux socket directories, `${TMUX_TMPDIR:-/tmp}/tmux-UID` and `/tmp/tmux-UID`, each by its physical path (5.177 point 6), closed (0000), where they exist.
  - So from a seat's view neither the workplace's server, tried by its real path, nor another tmux server of the user answers, though a row shows the places above them read-only.
  - `why` names the mask. `down` removes `RUN`, and the socket with it: tmux leaves its socket file however its server ends.

## The Logs layer: what a pane showed, kept and chained

- **C69.** The fold reads `record A B C SCOPE WHAT STATE`, `record-limit BYTES`, `record-chain SINK` and `record-path PATH`, and `reach`'s fourth action, `record`.
  - WHAT is `pane` or `programs`, STATE `kept` or `none`, and the scopes are a key's: the narrowest that speaks decides, and with no term nothing is kept. The limit is a whole number of bytes a seat's pane may fill in a day, 268,435,456 (256 MiB) by default. The sink is `journal` or `file`.
  - `view.json` gives `records`: the path, the limit and the sink. Each seat gets `record`, with whether its pane is kept, and `reach.record`, with the seats whose record it may read. With no term a seat reads no record, its own included.
  - `plan` refuses, with exit 1, leaving `PLAN/` as it was and naming the origins:
    - a term of the wrong form, scope, WHAT or state, a limit that is not a whole number above 0, or a sink the frame does not know;
    - `record … programs kept`, since the record of programs is built after the cutover;
    - two `record` terms of one scope and one WHAT with different states, and two `record-limit`, `record-chain` or `record-path` terms that differ;
    - `reach … record` with no `record-path`;
    - for the record path, everything it refuses for the mail path (C55), each naming the origins of the `record-path` term where C55's names those of the `mail` term, and a record path at, above or beneath the mail path;
    - a kept record of a seat with no view, since such a seat could reach its own record, except on an unenforced floor, whose seats have no view by design and read the machine as the user does (C104).
  - `plan` prints the records, whether each seat's pane is kept, and whose records it may read.
- **C70.** `build` makes `S/records`, and in it one directory for each seat, named by its name, each the user's with mode 0700. With floors S is the seat's floor's state (C102).
  - A seat's directory holds one file for each day by UTC, `DAY.pane`, and `unstored` and `gaps`, which only grow. `S/records` holds the carrier's `chain.state` and the file sink's `chain`.
  - `BUILD/records.json`, listed in the MANIFEST, holds the path with the origins of its term, the limit, the sink, the carrier's unit, and each seat's directory, its pane's state and whose records it reads.
  - `build` refuses a record path that is not a directory on the machine, or that lies in the state directory R or holds it, and `up` one that is no longer a directory. Each names the origins of the `record-path` term.
  - A plan that keeps a record needs `dd`, `date`, `tail` and `head`. One whose chain goes to the journal needs `systemd-run`, `systemctl` and `journalctl`.
- **C71.** `up` sets each kept pane's pipe after the pane terms and before the first start, so nothing the pane's program writes is missed. The pipe is `pipe-pane -O` into a keeper of the frame's, `workplace keep DIR LIMIT`.
  - The keeper runs outside every view, as a child of the server and under no-new-privileges, explicitly set on a floor, and it ends with its pane. The pipe outlives the start's `respawn-pane`.
  - The pipe's command quotes each word for the shell, and doubles its `%` and `#`, since tmux expands both in it.
  - The keeper stores what the pane's program wrote, byte for byte, with `dd`, a chunk at each read. It takes the day from `date -u` whenever the second changes, and changes the file itself at a change of day, so the pipe is set once. Setting it again loses lines: 2 in 20, measured.
  - At the limit it stores nothing more that day and counts what it does not store. When that day's file ends, at a change of day or when its pipe closes, it appends `DAY COUNT` to `unstored`. On tmux 3.8 a pane's pipe closes when its program ends; C98 says what tmux before 3.8 does.
- **C72.** With a sink, the carrier sends one entry for each kept file, every ten seconds and twice as it ends: for what was appended since that file's last entry. The kept files are each seat's day files, `unstored`, `gaps` and `signed` (C91), and the frame's record of requests (C66).
  - An entry is `{chain: "workplace-record", at, workplace, mark, seat, file, offset, length, hash, previous}`.
  - `mark` is the state directory's: 32 hexadecimal digits that `build` draws at random into `S/records/mark` when it is missing, and keeps across builds. `build` refuses a mark that is not a file holding 32 hexadecimal digits.
  - Its hash is the SHA-256 of `previous`, written as 64 lowercase hex digits, followed by the bytes from `offset` for `length`. Before a file's first entry, `previous` is 64 zeros.
  - The carrier keeps each file's offset and last hash in `chain.state`, across runs.
  - **The file sink:** appends each entry, one line of JSON, to `S/records/chain`.
  - **The journal sink:** `up` starts the carrier as a transient unit of the user's manager, `workplace-carrier-NAME.service`, with floors `workplace-carrier-NAME-F.service`, where each byte of the floor's key outside letters, digits and `_ . : -` is written `\xHH`, so that no key makes the name a pattern to `systemctl`, under `NoNewPrivileges` and `setpriv`, and refuses where no manager answers.
    - The ledger marks the unit by its invocation id, and `down` stops it through its manager: the unit is inactive when `down` returns.
    - The unit's `KillMode` is `mixed`: stopping it signals the carrier alone, which sends its last entries and ends. The programs it runs to hash an entry are not cut off, so no entry goes out with its hash missing.
    - The unit sets `SyslogIdentifier=workplace-carrier`, so the carrier's entries carry that identifier. `record verify` reads by unit and does not rest on it.
    - The carrier writes each entry on its standard output, which the manager hands to the journal stamped with the unit.
    - A run of the tests' own leaves about five lines of the carrier's in the journal, beside the manager's own lines about the unit.
- **C73.** In every view of a workplace that keeps a chain, the fixed part masks, after the rows and closed, `/var/log/journal`, `/run/log/journal` and `/run/systemd/journal`, where they exist. `plan` and `build` refuse a row other than hidden at or beneath one of them, naming the seat, the row and its origin, as at the clone. The user manager's socket and the session bus are closed in every view by C84.
- **C74.** On each pass the carrier reads every kept pane's pipe. Where one is gone, it sets it again and writes the time to the seat's `gaps`. It does not end the seat. The server tests the pane again in the same call that sets the pipe, so the carrier never closes a pipe that was set after it read the panes (tmux's `pipe-pane -o` would), and it writes to `gaps` only when that call set one (5.129 point 5).
- **C75.** `status` names, for each kept seat, its day file, its size against the limit and the byte the chain has reached, and, with the run up, its pane's pipe. It exits 1 for a pane without its pipe and while the sink's last entry was refused.
  - A refused entry moves nothing forward: the next entry the sink takes covers the same bytes, so a refusal leaves no hole.
  - Once the sink takes an entry again, `status` exits 0 for it, and names the time of the last refusal for the rest of the run.
  - `record verify NAME [DAY]` reads the seat's day file, today's by UTC by default, against its chain, taken from the plan's sink. From the journal, it takes only the entries whose `_SYSTEMD_USER_UNIT` is the carrier's unit and whose `mark` is the state directory's.
  - The carrier's unit is named by the workplace's name alone, so a workplace of the same name with another state directory sends its entries under the same unit. Its entries carry its own mark, and `record verify` passes over them. The file sink stands in S, so its entries are the state directory's by their place.
  - A build made before the mark holds no `mark` in `records.json`, and its carrier, which is the build's own loop, sends entries with none. `up` refuses such a build when its chain goes to the journal, with exit 1, and `record verify` with exit 2, each saying to build again.
  - It takes only the entries sent within the file's day and ten minutes on either side of it: from the journal it asks for that span alone, and from the file sink it takes the entries whose `at` lies within it. Its cost follows one day's entries, not the unit's whole history. Ten minutes hold the carrier's ten-second interval and a long pass of it many times over, so the entries of a day's last bytes stand within them. An entry sent later, by a carrier that was stopped without warning and started again after the margin, stands outside, and verify then says that the file's last bytes are not covered yet.
  - With floors `record verify NAME` reads the seat's floor's records and chain (C102), verifying that floor's build (C5), and `record verify --requests F` selects that floor's request record and chain; a missing or unknown floor is refused with exit 2.
  - `record verify NAME unstored`, `gaps` or `signed` reads that file of the seat, and `record verify --requests` the frame's record of requests (C66), each against its chain. These files are not a day's, so verify reads their chain over its whole span: from the journal, every entry of the unit, which 5.98 measured at about 4.5 seconds for each 100,000 entries.
  - It names the first place where file and chain differ, or says that they agree and up to which byte.
  - It exits 1 where they differ, and 2 for a seat it does not know, a day not written YYYY-MM-DD that is none of those three names, a workplace with no chain, and `--requests` in a workplace that holds no mail.
- **C76.** In a plan that holds a record path, the fixed part puts the frame's read-only file system at the record path in every seat's view, after the rows, whatever the machine holds there and whatever a row says above it. It holds one read-only directory for each seat whose record the seat may read, under that seat's name, and for a seat that may read none it is empty. `why` names it, and says for a seat that may read none that it is empty.
  - Since a seat with no view has no view to hold it, `plan` refuses, with exit 1, a seat with no row for `/` in a plan that holds a record path, naming the origins of the `record-path` term. An unenforced floor instead receives host links by seat name (C106), with the limits of C104.
- **C77.** No seat writes, cuts short, renames or removes a record, its own or another's, or makes a file beside one. A record stands in S, which no view holds, and the record path shows it read-only.
- **C78.** A seat that may read one seat's record reaches no third seat's through it, by a link, by `..` or by a name built for it. The record path holds only the directories the seat may read, each bound alone, and S is masked.
- **C79.** A pane's bytes are stored as they came: NUL bytes, bytes that are not UTF-8, formats, commands and escapes. None is read as a pattern, a format or a command by the keeper, the carrier or `record verify`: the keeper copies bytes, and the chain and `record verify` hash them.
- **C80.** `record verify` names a byte changed, a file cut short, a file removed and a line added in the middle, each at the first place it shows: the entry whose bytes no longer hash as sent, the byte where the file ends, or the file's absence.
- **C81.** A change of day loses nothing and doubles nothing. Measured: 3,000 lines, one a millisecond, across a forced change of day, each kept once and in order.
- **C82.** At the limit nothing more is stored that day, and the count of what was not stored is exact.
- **C83.** With the journal as the sink, an entry that another process sends under the carrier's words is not taken as the carrier's. `record verify` reads only the entries the journal itself stamps with the carrier's unit.

## The user's runtime directory

- **C84.** In every view, chain or none, where the seat's rows would show `/run/user/UID` as the machine has it, the nearest row at or above it being `read-only` or `read-write`, the fixed part puts there, after the rows, an empty file system, made read-only once the frame has put beneath it what it gives the seat.
  - **Why:** the user's manager answers there, through its own socket and over the session bus, and starts a unit outside every view for any caller of the user's; the user's ssh agent, the first program's sessions and the desktop keep their sockets there too.
  - **What it holds:** only the seat's own `hidden`, `searchable-only` and `scratch` rows beneath it, mounted again after the mask, and whatever the frame gives the seat beneath it. A seat's key agent is shown in its key home (C39), so a seat signs under the mask, and under a `hidden` row at the runtime directory as well.
  - **Rows:** a `hidden`, `searchable-only` or `scratch` row at the runtime directory stands as the text wrote it, and no mask is put there. `plan` and `build` refuse a `read-only` or a `read-write` row at or beneath it, naming the seat, the row and its origin, as at the clone. `why` names the mask, and the seat's rows beneath it that stand.

## An ssh key granted to a seat's agent

- **C85.** The fold reads `ssh-key NAME PATH` and `ssh-grant A B C SCOPE NAME STATE`. NAME is a word under the rule for a key of an office. PATH is as written, and the frame joins a relative one to the root. SCOPE is `workplace`, `floor` (C103), `office`, `room` or `seat`, with A, B and C as for `key`, and STATE is `granted` or `none`. For each NAME the narrowest scope that speaks decides, and with no term nothing is granted. A plan that holds either term is folded, so every seat of it has a view.
  - It refuses, naming the origins: two `ssh-key` terms of one NAME that differ, two `ssh-grant` terms of one scope and one NAME with different states, a NAME that no `ssh-key` term declares, a grant at a seat's own scope to a seat that holds no key, and a word, a count of words or a scope that the terms do not take.
  - It refuses a key's file that any seat's table shows read-only or read-write, naming the seat, its row and the key's term: no seat is shown the file of a private key.
  - A grant of a wider scope reaches the seats of that scope that hold a key. `plan` prints each key with its file, and, for a key that no grant takes to a seat that holds a key, that it reaches no seat. It prints for each seat the names it is granted, with their terms, and, for a seat of the scope that holds no key, that the grant does not reach it. `view.json` gives each seat `ssh: {granted, unreached}`, and the keys under `ssh.keys`.
- **C86.** `build` checks the file of each key that reaches a seat, once and before it makes any key home, with `ssh-keygen -y` and an empty passphrase, under `setsid` with nothing on standard input. It refuses with exit 1, naming the key and its file: a file that is missing or is not a regular file, one that asks for a passphrase, one that ssh does not read as a private key, an RSA key under 2048 bits, a security key's file, and any kind but ed25519, RSA and ECDSA on nistp256, nistp384 or nistp521.
- **C87.** For each holding seat that a key reaches, `build` loads the key into the seat's home, after the seat's own: through an agent of the home started with `--batch` on its command line, by `ssh-add` reading the file on its standard input, and it ends that agent. The file is read by `build` alone, outside every view: once for the check and once for each seat, and nothing of it is kept between the reads.
  - The home gains one unprotected key file per grant, and its grip in `sshcontrol` after the seat's own, which the agent offers first. `sshcontrol` is made read-only once the keys are loaded (C35).
  - The home gains `ssh/NAME.pub` for each grant, read-only: the public OpenSSH line with NAME as its comment.
  - `keys.json` gives each holding seat `grants`: for each, its NAME, that line, its SHA256 fingerprint, the grip of the key and its kind. No byte of a private key stands in `BUILD`.
  - The copy in a home is a key of that build: every build removes the old homes, and their copies with them (C36).
- **C88.** The agent of each home has `disable-scdaemon`: no smartcard daemon runs for it after a listing.
- **C89.** `up` refuses with exit 1, naming the file, a home whose `gpg-agent.conf` says `batch`, and a machine whose `gpg-agent.conf` in GnuPG's system directory says it, since every agent reads that file and an agent with `batch` takes any key added through its ssh socket. It checks that each agent offers every key the build loaded for it, refuses where one does not, and records the agent's answer among the run's checks.
- **C90.** A seat that a key reaches is shown, in G at `ssh/`, the public files of its keys, read-only. Through its ssh socket it lists each granted key after its own and signs with it.
  - A key loaded on standard input shows the file's own comment, or `(stdin)`, and never a path. A seat tells its keys apart by their public files.
  - Through the two sockets it is shown it obtains nothing of a granted key, adds none and removes none, as for its own (C41). No file of the key stands in its view.
  - Its ssh configuration, which the workplace's text writes, names the key's public file for each host and offers only that one. A host that allows one try logs it in so, and refuses an agent that offers every key, since the agent offers the seat's own first.
- **C91.** Where the plan keeps a record, each holding seat's agent logs at `-v` to `signed`, in the seat's directory of records, with its times in UTC, and the carrier chains `signed` among the kept files (C72). After an ssh signature it holds a line with the second, and nothing of the key or of the data.
- **C92.** `status` lists each agent's granted keys by name, and exits 1 when an agent no longer offers one that the build loaded. `why` names a seat's grants, the terms that give them and their public files, and for a seat that holds no key, the grants that do not reach it.

## The wake: a delivered mail pointed out to its reader

- **C93.** The fold reads `wake KIND PATTERN`, once for a kind. PATTERN is a POSIX extended regular expression, matched as bash's `=~` matches it in the loop's C locale, byte by byte. With no term a kind's seats are not woken. A plan that holds the term is folded.
  - `view.json` gives each seat of the kind `wake`, with the pattern and its origins, and `plan` prints it for each such seat.
  - `plan` refuses, with exit 1, leaving `PLAN/` as it was and naming the origins: a term of the wrong form; a kind the plan does not make; an empty pattern, which finds every screen ready; a pattern that holds a control character, C0, DEL or C1, which `build` refuses in a plan (5.162 point 5); two terms for one kind with different patterns, while equal ones count once; a pattern that bash refuses; and a wake with no mail term. `build` refuses a pattern that bash refuses in a plan written by hand.
  - **A kind's own wake** (5.146): `wake-own KIND MODE ITEM` says that the kind's program has been measured to wake by itself on a floor of MODE, `enforced` or `unenforced`, as the definition's item ITEM rules. The house's source writes it only after such an item, and the frame measures nothing and carries ITEM as written: it refuses an empty one, which names no item and would leave the line `plan` prints without one, and one that holds a control character, which would break that line and could be lost where the carrier reads the item back, so that for every item the fold takes, what `plan` prints and what the carrier decides agree (5.153). `view.json` gives a seat's `wake` an `own: {mode, item, origins}` where its kind has one for its floor's mode, `plan` prints it, `why` names it for the seat, and with floors `mail.json` gives each seat `own`: that item, or `null` (C56). `plan` refuses, with exit 1, a term of the wrong form, a kind the plan does not make, a mode that is neither, an empty item, an item that holds a control character, a kind with no `wake` term, since a kind that wakes by itself keeps its pattern for the pointers that stay, two terms of one kind and mode with different items, and a term in a plan without floors.
- **C94.** At delivery the carrier decides once for each reader, out of four (5.146): **none**, for the mail's writer and for a reader whose kind has no wake; **withheld**, with floors, where the reader's room is cleared more than the writer's (a smaller number, a room with no number cleared least, the numbers read on every floor) and the reader's kind wakes by itself on its floor (C93); else **due**; and **typed**, once a due pointer is typed. The writer is told only that its mail was delivered. Once the carrier delivers a mail to a reader whose kind has a wake, that reader has mail to be pointed out, unless the reader is the mail's writer or its pointer is withheld. A mail that a seat sends itself, and a mail whose pointer is withheld, is delivered and is not pointed out: the count and the newest id come only from mail decided due, whose writer, as the carrier writes it in `from` (C59), is another seat. After each pass, for each such reader that had no pointer in the last minute, the carrier looks at the visible screen of the reader's pane, never at its history.
  - The pane is ready when tmux shows it in no mode and one of the last five lines of that screen that are not empty matches the pattern. Then the carrier types one line, and `Enter` after it in a call of its own a second later, through the function that types a write (C60): `mail: N new, newest ID.md, in PATH/in, and the page PATH/README.md says what this line is`. N is the count of mail due to that reader since its last pointer, in decimal: every mail delivered to it since then that the carrier decided due, so neither one whose writer is the reader nor one whose pointer was withheld. ID is the newest of those mails' id, and PATH is the mail path, where the seat sees its mailbox. Then the mail that the pointer counted is no longer to be pointed out to that reader, and mail delivered to it meanwhile, by another floor's carrier, stays to be pointed out (5.162 point 1).
  - The function types every mail path that `build` takes as it stands. `build` refuses one with a character that moves or breaks a line (C55), and `send-keys -l` types the rest literally: a space, a comma and a `;` inside the line, measured byte for byte. The line ends in `README.md` and so never in `;`.
  - That function checks the mode too, beside the mark. A pointer that meets a mode there is recorded as refused, and its mail stays to be pointed out.
  - What is to be pointed out outlives the run. It stands in `wake.json`, and after `down` and `up` the carrier goes on from it, with the same count and the same newest id.
  - It types nothing else of its own accord, and nothing into a pane that is not ready. The line holds no byte that a seat wrote: the count, the id and the mail path are the frame's own, and a mail's subject, body and writer, and a request's name, do not enter it.
  - At most one pointer goes to a reader in a minute.
- **C95.** `status` lists each seat with mail to be pointed out: how many, by the same count, which holds no withheld mail (C96), and the time the first was delivered. A seat's own mail puts it in no list. A seat that works, that sits at a question of its own program, or whose pane is in a mode, stands in that list until its pane is ready. `status` does not exit 1 for it.
- **C96.** Each pointer is one line of the record (C66): the time, `the frame` as the one who asked, the action `wake`, the reader as its target, the ids it covers, the outcome, and the length and SHA-256 of the line typed. Each `none` and each `withheld` decision is one line too, at delivery, with no length: the time, `the frame`, the action `wake`, the reader as its target, the mail's id as what it covers, the outcome, and the reason, which for `withheld` names both rooms' numbers and the `wake-own` item. Nothing withheld enters `wake.json` or `status` (C95), and the record holds all four.

## What a seat is told about mail: the frame's page

- **C97.** Every mailbox holds `README.md`: the frame's page for a seat. Its text is `share/seat-page.md` in the frame's repository, the same in every mailbox, and it names no seat, no workplace and no path.
  - `build` copies it into `BUILD/seat-page.md` when the plan holds mail, and a plan without mail gets none. The fixed part shows that copy at `PATH/README.md`, read-only, in the mailbox's file system, which is read-only too, so a seat can neither change the page nor put another in its place. `up` refuses a build with mail that holds no page.
  - The page says what the pointer's line is and that no person typed it; what the four parts of a mailbox are; that the frame writes `id`, `at` and `from`, and that `from` is a sender's only identity; how a mail is sent and where its answer stands; that grab and write exist and are refused where they are not allowed; the form of each, as C60 gives it, and what its answer holds; and that a `C-c` ends a pane whose program is plain, and its seat with it.
  - The forms of a request are defined here, in C57 to C60, and told to a seat by the page alone. Every suffix and every word of a head that the page names is one that the carrier takes.

## Starting a seat again, and removing a build

- **C98.** A seat's pane stays when its program ends, dead and in its place: `start` sets the pane's `remain-on-exit` before it starts the program. Its id, its place in the window, the session's mark and the carrier's slots stay as they were. `status` names the seat as gone and exits 1. The carrier types nothing into a dead pane and does not set its pipe again.
  - **What becomes of the pane's pipe.** tmux 3.8 closes a pane's pipe when its program ends, so the keeper ends with the program and writes its count (C71). tmux 3.5a to 3.7c keep a dead pane's pipe open: their `server_destroy_pane` closes the pane's terminal and not its pipe, and `pipe-pane` refuses a dead pane. In the pipeline on 3.5a, a pipe set on a pane stayed open after its program ended, and its reader had no end of its input until the server ended; and in the frame, a keeper of the dead pane's record still ran after its program had ended. `restart`'s `pipe-pane` closes an old pipe before it sets its own. On both versions the count of what was not stored is exact, and stands once, by the time `down` returns (C82). When it is written on 3.5a while the pane is dead is among the limits.
  - `workplace restart [SEAT ...]` starts again each named seat, or with no name each seat whose program has ended, and leaves every other pane as it is. For each, it makes the pane ready with a waiting program and sets a kept pane's pipe as `up` does, both in one call of tmux, so the carrier never finds the pane alive with no pipe (5.129 point 5). It then runs the seat's own start from the run's calls again: the same view, environment and command.
  - It refuses what `up` refuses, and then starts nothing: a build that does not verify; a missing program; a server that is not the run's; a seat whose start `exec --print` refuses; values, homes, mail and records as `up` checks them; and any other line of the run's checks that `status` names as gone, the carrier's and the agents' among them. It refuses with exit 2 a seat it does not know, a pane that is gone or lacks the run's mark, and a workplace that is not up, and with exit 1 a seat whose program runs.
  - It records who asked: one line of JSON in `S/restarts`, mode 0600, with the time, the seat, its pane, and the user, the uid and the terminal of the shell that asked, and, for a kept pane, a line in the seat's `gaps`, which the chain covers. It says the same on its output.
  - With floors (5.160 point 8), `workplace restart F [SEAT ...]` starts again seats of the floor F alone, holding the floor's lock until it ends (C20, C102). A bare `restart` is refused with exit 2, and so is a seat of another floor, as one it does not know. Its record is the floor's, `S/floors/F/restarts`.
  - The mail that waits to be pointed out to the seat stays (C94). Its count and newest id come with the next pointer, once the new program's pane is ready.
- **C99.** `workplace unbuild` removes `BUILD` while the workplace is down. It refuses with exit 1 while `RUN` stands. With floors it refuses with exit 1 while any `RUN/F` stands, naming the floor, and removes an empty `RUN`. Before it reads `RUN` or `BUILD` it takes, each without a wait, the build's lock wherever it stands, whatever the build's layout, since a build of floors writes its top last, and the lock of each floor whose state stands, making a missing one with mode 0600, so that the first `up` of a floor after a build is fenced too; it refuses with exit 1 one that another command holds (C102). It names each file it removes and the MANIFEST's hash. With no `BUILD` it says so, and goes on.
  - Then it removes the homes of `S/keys` as every build does before it makes new ones (C36): their runtime socket directories first, which ends any agent of them, then the homes. It names each home and how many files it held. It does so also when no `BUILD` stands and key homes do.
  - It finds S where the build's records name it while `BUILD` stands, and otherwise by the workplace's name (C25): the one that the build's plan (`BUILD/plan.json`, or with floors the shared generation's, C5) or else `PLAN/plan.json` gives when it is `default` or the clone's derived name, and else the clone's derived name.
  - It names the state directory and keeps everything else in it: the seats' homes, the records, the mail's store, the values file and `restarts`. It exits 0.

## Floors and rooms

- **C100.** `workplace.json` may hold `floors`, a list of one or more floors, each with exactly `key`, `name`, `houses`, `enforced`, `socket`, `conf` and `smallest` (5.116, 5.117, 5.123, 5.124 points 1 and 2).
  - **The members.** A key follows the rule for a key (C67), and no two floors share one. A name follows the rule for a name and holds no colon between spaces, nor one at its start or end beside a space (C27, 5.142). `houses` is `offices` or `rooms`, and `enforced` is `true` or `false`. `socket` is `run` or `tmux-default`, at most one floor takes `tmux-default`, and an enforced floor takes `run`. `conf` is a relative path to a file in the clone that is not a link, not empty, and, as the root program holds it, holds no colon between spaces nor one at its start or end beside a space (5.142). The members are read so that each keeps its place, an empty word or a backslash among them (5.141 point 7). `smallest` is written `COLSxROWS`.
  - **What else changes.** With `floors`, `workplace.json` holds no `socket` and the clone no `tmux.conf`. A `socket` beside `floors` is refused by that one line, and its value is not judged (5.135). The name is the derived one (C25). Each floor's file is an input, in the floors' order, where `tmux.conf` was.
  - **The root program.** It is `workdir : ROOT`, `workplace : NAME`, and a line `floor : KEY : NAME : HOUSES : ENFORCEMENT : SOCKET : CONF : SMALLEST` for each floor, under the derivation `root-floors-v1`.
  - **What `plan` refuses.** It refuses each fault of these with exit 2, naming it.
- **C101.** In a plan with floors the structure is checked at `plan` as well as at `build`. It holds no `server` and exactly one `workplace`.
  - **The counts of servers and floors** (5.135, 5.136). A plan holds one server and no floor, or no server, one workplace and at least one floor, and each count outside these is refused by one line, at `plan` and at `build`: no server and no floor, and servers beside floors, by that sentence; two or more servers with no floor by C3's line, which names the terms and which `plan` runs as well.
  - **Offices.** Each office stands in exactly one `house F A` of a floor that houses offices. A house that names a key that is no floor is refused as naming a floor that the plan does not make (5.131 point 4).
  - **A floor of rooms** stands for its own session. It has no `session` and no `house`, and its rooms are `window F R NAME`.
  - **The keys.** No key names both a floor and an office. The refusal names every term in which the key stands as a floor or as an office: the floor's term, each `house` term that names it, and each `session` term of that office, not one whose name only equals the key (5.135).
  - **Every floor** holds an office or a room. A floor of rooms that holds none is refused by that line alone: no other line follows for it, and no line calls a floor's term a session term (5.131 point 4).
  - **Without floors,** a `workplace` or `house` term is refused.
  - **Floors up** (5.160 point 8, 5.167). With floors `up`, `down`, `restart` and `carry` name one floor, and refuse with exit 2 none, two, or one the build does not make. A `tmux-default` floor uses the caller's default socket. `up` refuses a foreign or barred server there with exit 1 before changing its sessions, options, hooks or environment. Each test uses a private `TMUX_TMPDIR` mode 0700 and refuses the real socket directory before sending a command. An unenforced floor's server and seats run without the bar, on a run socket too. Its mailboxes and allowed record links stand on the machine by seat name.
- **C102.** With floors, a floor's state is `S/floors/F`, mode 0700. `build` makes `S/floors` and `S/floors/F` with mode 0700, and refuses with exit 2 either one that stands with another mode, naming it and its mode, as it refuses S (5.129 point 6).
  - **The build's own state** (5.162, the addendum's Q8). With floors, S also holds the build's lock `build.lock`, its holder `build.holder`, the generations' lock `generations.lock` and the counter `generation.next`, each a file of this user's with mode 0600 that `build` makes. `build` refuses with exit 1 one of another kind or mode, naming it, and, after a wait of two seconds, a lock that another build holds, naming the holder's command, process and time. It needs `flock`, and refuses with exit 2 where no state directory can be named. It holds the lock until it ends, and every process it starts has the lock's descriptor closed, so that none holds it after the build.
  - **What stands in it.** Its seats' key homes (`keys/NN`, NN their place among that floor's panes), kept homes and records stand there, and the build's files for them stand in the floor's generation `BUILD/floors/F/N`, listed in its MANIFEST, which the top names (C5).
  - **The floor's locks** (5.160 point 8, 5.176 point 12). `S/floors/F/up.lock`, with its holder `up.holder`, is the floor's lock, which `up F`, `down F` and `restart F` hold until they end (C20). A competing command refuses immediately with exit 1 and names the holder. Daemons do not inherit that lock. `up.lock` and `up.holder` are files of this user's with mode 0600, and one of another kind or mode is refused with exit 1, naming it. `S/floors/F/carrier.lock` is the floor's carrier's (C57).
  - **What stays in S.** The store, the comms but each floor's `taken` and `serving` (C56), and the values stay in S, one for the configuration (5.125 point 13).
  - **`unbuild`** removes the key homes of S and of every floor's state.
- **C103.** The fold knows the scope `floor`, written `F - - floor`, ranked between `workplace` and `kind`. It holds the seats of every office housed on the floor, or of every room of a floor of rooms. `statement`, `key`, `expect`, `record`, `ssh-grant` and `reach` take it, and `clearance` does not.
  - **Typing the first position.** It is a floor's key exactly when a `floor` term names it, and an office's key otherwise. A term at an office's scope that names a floor refuses the plan, and so does a term at a floor's scope that names an office (5.125 point 1).
- **C104.** A floor is enforced or not.
  - **A seat of an unenforced floor** has no rows, no labels and no view. It is not refused for want of a row for `/` (5.124 point 3).
  - Its ordinary user privileges remain. Labels, privacy and identity restrictions on this floor are conduct: host files and other processes of the same Unix user remain reachable. Mail and record links do not enforce those restrictions.
  - **On an enforced floor the room is one view.**
    - A statement at a seat's scope refuses the plan (5.124 point 5).
    - A kind's statements are folded into every room that seats the kind, at the room's scope, with their own terms and origins (5.125 point 4).
    - Two statements of different states about one path at one room refuse, naming every origin. Equal ones make one row with all their origins.
    - Every occupant of a room carries the same rows.
    - An asking `reach` at a seat's scope, in a room of several, refuses (5.118).
  - **`view.json`** gains `floors`, each seat's `floor` and `enforced`, and `rooms`, one entry for each room of an enforced floor. Each entry holds the room, `of` (`office` or `floor`), its floor, its clearance, its occupants and its rows keyed by the room.
  - **`plan` prints**, when it folds the plan, each unenforced floor, and each room of an enforced floor that has no number (5.125 point 7), least among its office's rooms, or its floor's on a floor of rooms. Since 5.146 point 7 it also prints each room of an unenforced floor that has no number, since the pointer's direction reads it as cleared least. A plan it does not fold prints none of these lines.
  - **A plan that holds an enforced floor and no fold term** refuses at `plan` and at `build`, with exit 1, one line for each enforced floor in the plan's order: `the floor F is enforced, and the plan holds no fold term: an enforced floor's rooms are folded from statements, and the plan's view cell, which gives each seat rows of its own, is refused there (5.129 point 4)`. `plan` closes with `the plan holds an enforced floor and no fold term; PLAN/ is as it was`, and `build` with `build refuses: PLAN/plan.json holds an enforced floor and no fold term`. A plan whose floors are all unenforced and that holds no fold term takes its view cell, as C33 says.

## Limits, stated and not checked

- A mail's body is carried byte for byte, since mail carries captures and logs, which hold control characters. The head is the frame's, and it ends at the first line of three dashes; a reader takes `from` from the head alone. A mail shown raw on a terminal can draw over its own head, so a mail is read through a program that does not obey control characters, as a seat's file tool does.
- A C-c typed into a pane whose program is plain ends the view with it, before the program's own handler runs: it reaches the whole foreground process group, the view's bubblewrap included, which ends and takes the program with it. A shell with job control and a full-screen program are not touched. It was measured on a workplace of its own: a C-c typed from outside the workplace into the panes of two seats whose programs were plain, with no job queued, ended each within three seconds with its view, nothing started either again, and `status` named both as gone. Such a pane now stays, dead, until `restart` or `down` (C98). The frame does not refuse such a write: a write's key may be `C-c` (C60), and the frame does not tell a plain program from another. That no C-c is written into a plain pane is a rule for whoever writes a write request.
- A read-only row does not close a socket. The fold knows files: a socket that any row shows, read-only included, gives the seat whatever its listener does for the user, and an abstract socket, which has no file, is reached by every seat that shares the machine's network. The frame closes its own: the server's (C68), each agent's (C39), the user's runtime directory with the manager, the session bus and the user's agents in every view (C84), and the journal's where a chain is kept (C73). For the rest, a workplace's text hides the places where the machine keeps sockets: `/tmp` and `/run`. An abstract socket stays reachable: the kernel's Landlock can scope a process to the abstract sockets of its own domain, but neither `setpriv` nor bubblewrap offers that scope yet.
- **A row holds the object at its path, not the name.** It shows the file or directory that stood at its path at `up`, under the row's state, for as long as the seat's view stands, and it does not keep that name on the machine.
  - Beneath a row that shows the machine's directory, whoever writes that directory from outside the seat's view, another seat's view or a process of the user, can put another object at the name: a new file renamed over a file, or a directory removed and made again. The seat's row is then gone, and the seat sees the new object as the parent row shows it. A `read-only` row beneath a `read-write` one becomes writable so, and a `hidden` directory shows what the new one holds.
  - Where a directory lies between a row and its `read-write` parent row, the seat itself can rename that directory and make the path anew. Its row stays on the old object, and the name on the machine is then the seat's.
  - The seat cannot do this to its own row's path, which is a mount point in its view: a removal or a rename over it is refused. A row beneath a `hidden`, `searchable-only` or `scratch` row is not touched, since its mount point stands in a file system that the view made.
- `restart` records the account and the terminal that asked, not the person: anyone who runs the frame as the user can start a seat again.
- **A dead pane's count on tmux before 3.8.** On tmux 3.5a, in the pipeline, a count of what was not stored stood in `unstored` while the pane was dead and a keeper of its record still ran, before `down`; after `down` it stood once and exact. Who wrote it then is not yet measured, and the test prints the keepers it finds and `unstored`, so that the pipeline shows it.
- A process of the user outside every view can stop the carrier or its unit, edit or remove a record, or move a process of its own into the carrier's unit and send under its name. An edit shows to `record verify`, and a stop as a gap in the chain. What the carrier had not sent when it was stopped without warning is the part that no entry covers.
- The keeper takes the day from `date -u` on the path that `up` was given, and the carrier sends its entries every ten seconds and as it ends.
- A keeper that a signal ends does not write that day's count of what it had not stored. The carrier sets the pipe again and records the gap.
- The journal keeps what it is sent within its own rate limit and retention, which are the administrator's. On this machine they are the defaults: a rate limit of 10,000 entries in 30 seconds for a unit, and removal by size and not by age. The carrier sends an entry only for a file that grew in the last ten seconds, so a house of 28 seats sends a few hundred in 30 seconds at the most. An entry that the journal dropped, or has since removed, shows to `record verify` as a skip.
- A seat's home (C47, C48):
  - **A scratch home's further directories.** The frame makes no further variable's directory in a scratch home. The home is empty when its pane starts, and the seat's program makes them. The frame would need an entry of the fixed part that makes a list of directories, which it does not have.
  - **A further variable names a directory, never a file.** `build` makes each further variable's path a directory in a kept home (C47), so a further variable cannot name a file. A variable that names a file would be a term of its own, which the fold does not have.
  - **A home changed while `build` runs.** `build` checks each name below a kept home before it makes the next. A seat that runs while `build` does, and puts a link there between the check and the making, has `build` make the directory where the link points.
- A seat's program has no session bus, and so no notification, no secret service and no portal, and it has no manager of the user's (C84).
- A granted key (C85 to C92):
  - **Copies.** Each holding seat's key home holds an unprotected copy of every key granted to it, for as long as the build stands. A key granted to every holding seat stands once in each of their homes. The copies go with the build's homes (C36).
  - **The extra socket.** A seat signs any hash with a granted key through its extra socket too, and such a signature leaves no line in `signed`. The agent's own log cannot name the key behind an ssh signature without also writing the private keys, so `signed` names the seat and the second, and the accepting host's record names the key and the account.
  - **The agent's answers.** It answers `ssh-rsa` signatures with SHA-1; which signatures a host takes is the host's. Lock answers success, and the agent still lists its keys.
  - **Use.** A seat uses a granted key for as long as it runs, and it can forward its agent to a host for the length of one connection. A process of the user outside every view reaches the state directory, and the homes in it.
  - **Who runs `build`.** A workplace that names a key is built outside its own views. A seat of another workplace that runs the build was shown the key's file by that workplace's text. The frame does not see across workplaces.
  - **Where no record is kept,** a holding seat's agent logs nothing.
  - **What `status` compares.** `status` compares each agent's whole answer to `KEYINFO --ssh-list --ssh-fpr=sha256` with the one `up` recorded, and not its keys alone. A change in any other field of that answer exits 1 too, as if a key were gone.
- The wake (C93 to C96):
  - **Ready is what the pattern says of a screen.** A program that shows its input box while it works is typed into while it works. A kind's pattern is to match only what its program shows when it waits for a line.
  - **Typed is not read.** The frame knows that a pointer was typed. It does not know that a mail was read.
  - **A kind with no wake.** Its seats are reached as before: by a writer that may write their panes (C60), or by their own look.
  - **The carrier's own stops.** A pointer that tmux does not take is recorded as refused, and its mail stays to be pointed out. A carrier stopped without warning between a delivery's commit and the end of its decisions decides, as it starts again, for each reader it had not decided for (C94). What it had decided as due and not yet saved in `wake.json` is decided again then, from the time of the delivery's commit.
  - **A mode entered after a look.** The carrier looks at the pane, in the call that checks the mark, before it types the text and again before it sends the key (C60). A mode entered between the first look and the text takes the text, and the second look refuses the key, as C60 says. A mode entered after the last look takes what comes after it, the key, or the text when the key is `none`: the write or the pointer is recorded as `ok`, and its program reads none of it.
  - **The C locale.** A pattern matches byte by byte (C93). A literal of any script matches as written, so `❯` works. A bracket expression with a character of more than one byte matches each of its bytes alone, and `.` matches one byte. A kind's pattern for a program whose prompt is not ASCII writes the character outside brackets.

## Floor configuration application (4a2)

- **C105.** Each floor generation seals `floor.conf`. The top also seals the floor runtime module and both `share/floor-set-*.conf` files. A new server reads its sealed configuration and then its mode's frame settings; source edits require a new plan and build. Active hooks, parse errors, a file-created session and shell expansions in enforced-floor options are refusals before any occupant starts. A floor's tmux calls have at most a ten-second deadline, with a one-second kill fallback; the initial default-socket probe has a two-second deadline. Their output is captured in a private temporary file and copied after the client ends, so a stopped server holding a client's output descriptor cannot keep a command substitution open beyond the deadline. Floors need `timeout`, `mktemp` and `cat` for this capture. A server whose refusal cannot be cleaned up without ending an unowned session retains its run directory for inspection.

  The frame disables synchronized input, preserves at least 5000 history lines, resets command aliases, clears reserved option shadows at startup, and sets its clone, floor and configuration-digest marks. Each session disables destroy-unattached. Each enforced pane enables alternate-screen and disables passthrough; the unenforced floor retains non-transport choices. Higher history limits remain unchanged. An existing pane with insufficient history is refused. Hook checks include global session and window scopes, local session, window and pane scopes, and monitor subscriptions where the running tmux supports them. Enforced-floor option checks include those local scopes. An owned default server is reused only when its recorded configuration digest matches the sealed file and its command aliases match the digest recorded on initial admission: tmux ignores later clients' `-f`, so a changed file requires the user to end that server before `up`. This refusal leaves its personal sessions and settings unchanged.

- **C106.** The carrier reads back transport settings, repairs a difference it can repair, and appends a frame-set restoration event. With refused hooks, a forbidden expansion or a missing server, mail delivery continues and the refusal is recorded; screen access and typing wait for valid transport. A mail-only run with no pane slots needs no terminal context. A run with panes must name its frame settings. `status` reads back and reports a disagreement without repairing it. These checks do not turn an unenforced floor into confinement.

  An unenforced mailbox is `MAILPATH/NAME/` and holds the in, sent, out, answers and README links that build made. Its record view is `RECORDPATH/NAME/`. Up and restart verify them and refuse collisions or missing links. A marked server is also checked against the floor's recorded privilege mode when status, down or restart reads it. For a default-socket floor, down removes only its own sessions and RUN/F, retaining personal sessions, the server, global frame settings, aliases and reserved clone/floor marks. A carrier unit of a different invocation is left alone, even when two workplaces use the same name.

- **C107.** Each hold of the shared mail store gives carrier Git calls a shared five-second deadline, with a one-second kill fallback. Git children retain the store lock after a carrier dies; another floor cannot enter until those children end. On acquiring that lock, and after a failed Git call, the carrier removes stale `.git/*.lock` and `.git/refs/**/*.lock` files owned by this user, never object-store files. A Git process started outside a carrier is unseen and must obey the store-lock convention. A failed or timed-out commit is reconciled from the store before its copies are removed: if that read cannot complete, the serving journal remains for a later recovery hold. The reference-transaction check kills inside a real prepared delivery, proves that the orphan holds the shared lock, and measures another floor delivering after its deadline; a committed-then-blocked variant preserves and acknowledges the committed mail.

- **C108.** Each floor appends and chains its own request record at `S/floors/F/comms/record`, with one carrier writer; no shared-store lock is required to append it. Without floors its path remains `S/comms/record`. Before a request is renamed into `taken`, a durable serving journal identifies its original box, name, action, record offset and stage. Recovery returns an unserved request without overwriting a newer request, restores a journalled answer and completed record without duplicating its line, and records an interrupted terminal action as unknown. A Git range that cannot be read is retried in three recovery holds, then refused as uncertain with its copies retained and inspection required. `record verify --requests F` verifies the named floor; omitting or misnaming that floor is usage error 2.

- **C109.** Before typing each wake pointer, the reader floor stores its covered IDs, target, text length/hash, start time and record offset in an atomic per-seat journal. After a kill without a recorded outcome, recovery appends one unknown line, keeps the IDs due, and sets the original attempt time for the retry interval. A successful journal settles only its covered IDs; later mail stays due. Its local record is written before a shared-store hold is obtained. Status subtracts successful but unsettled pointer IDs. The destination floor typing lock serializes the ready check, text, pause and key, and tmux children close that lock descriptor. Every carrier tmux call has a three-second deadline with a one-second kill fallback. These journals cover process interruption; this is not a power-loss/fsync guarantee.
